# ТЗ: Система выдачи аналитических форм журнала посещаемости пар (КамчатГТУ)

**Адресат:** DeepSeek V4 Flash (Max Effort)
**Роль агента:** спроектировать и предложить реализацию модуля отчётности поверх существующей системы учёта посещаемости (данные о занятиях, группах, студентах, преподавателях, дисциплинах уже собираются — см. раздел «Входные данные»).
**Формат ответа агента:** архитектурный документ + при необходимости стаб-код (TypeScript, если реализация встраивается в существующий Bun/Electron-стек проекта).

---

## 0. Контекст и входные данные

Считать, что уже существует источник данных журнала посещаемости со следующими сущностями (агент должен явно зафиксировать финальную схему перед проектированием отчётов):

- `Institute` (институт, напр. ФИТЭУ)
- `Department` (кафедра)
- `Group` (учебная группа, курс, форма обучения)
- `Student` (ФИО, номер зачётки, группа)
- `Teacher` (ФИО, кафедра, дисциплины)
- `Subject` (дисциплина)
- `Lesson` (пара: дата, время, № пары, группа, дисциплина, преподаватель, аудитория, тип занятия)
- `AttendanceRecord` (студент, пара, статус: присутствовал / отсутствовал / опоздал, причина отсутствия: уважительная / неуважительная / не указана)

Агенту нужно спроектировать **модуль генерации отчётов**, который читает эти данные (через абстрактный `ReportDataSource`, не завязываясь на конкретную БД) и выдаёт аналитические формы согласно требованиям ниже.

## 1. Какие формы нужны

Спроектировать набор отчётных форм, разделённых на уровни агрегации. Для каждой формы агент должен определить: **назначение, входные фильтры, состав колонок/полей, единицу измерения показателей, кто является типовым заказчиком**.

### 1.1 Формы по группе
- **Ведомость посещаемости группы за период** — таблица «студент × дата/пара», статус по каждой ячейке, итоговый % посещаемости по студенту и по группе.
- **Сводка пропусков по группе** — количество пропусков (уважительных/неуважительных/опозданий) по каждому студенту за период, с сортировкой по убыванию.

### 1.2 Формы по студенту
- **Персональная карточка посещаемости** — детализация по всем дисциплинам за период, с разбивкой по типам занятий (лекция/практика/лабораторная).
- **Справка о посещаемости** — краткий официальный документ (для деканата, стипендиальной комиссии, военкомата и т.п.), формат — почти всегда Word/PDF, не Excel.

### 1.3 Формы по преподавателю / дисциплине
- **Журнал заполнения преподавателем** — контроль дисциплины: сколько пар отмечено, сколько пропущено отметок (для проверки дисциплины ведения журнала).
- **Посещаемость по дисциплине** — агрегация по всем группам, изучающим дисциплину, с разбивкой по группам.

### 1.4 Формы уровня кафедры/института (управленческая аналитика)
- **Сводный отчёт по кафедре/институту** — средний % посещаемости по группам/курсам, тренд по неделям/месяцам.
- **Рейтинг групп/курсов по посещаемости** — топ и антитоп для деканата.
- **Отчёт по причинам отсутствия** — доля уважительных/неуважительных пропусков, для выявления системных проблем (напр. массовые пропуски по конкретной дисциплине).

### 1.5 Оперативные формы
- **Экспресс-отчёт «на сегодня/на неделю»** — для старост и кураторов, без сложных фильтров, быстрый просмотр.
- **Отчёт о хронических прогульщиках** — студенты, чей % посещаемости за период ниже настраиваемого порога (напр. < 60%), для передачи в деканат/на отчисление.

> Агенту зафиксировать это как перечисление `ReportType` (enum) и для каждого типа — интерфейс параметров (`ReportParams`), т.к. UI меню заказа (раздел 4) строится поверх этого перечисления.

## 2. Форматы экспорта

Каждая форма должна поддерживать экспорт минимум в один из форматов ниже; часть форм (табличные) — во все три.

| Формат | Когда применять | Технические требования |
|---|---|---|
| **PDF** | Официальные справки, ведомости для печати и подписи, отчёты для деканата | Фиксированный макет, поддержка кириллицы, колонтитулы с шапкой КамчатГТУ (институт/кафедра/дата формирования), место для подписи/печати на официальных формах, пагинация при большом числе строк |
| **Excel (.xlsx)** | Аналитические формы с большим объёмом данных, сводки, рейтинги | Отдельный лист под каждую группу/период при больших выборках, автоширина колонок, условное форматирование (напр. подсветка низкой посещаемости), сводные таблицы для управленческих форм, заморозка шапки |
| **Word (.docx)** | Справки, официальные письма, докладные записки с текстовым сопровождением | Использование шаблонов (letterhead КамчатГТУ), поддержка вставки таблицы в текст документа, готовый к печати и подписи вид |

Дополнительно агенту предусмотреть:
- Единый **шаблонизатор** (одна модель данных → рендер в PDF/XLSX/DOCX через разные рендереры), чтобы не дублировать логику агрегации под каждый формат.
- Возможность **предпросмотра** формы перед экспортом (см. раздел 3.1).
- Асинхронную генерацию для тяжёлых отчётов (институт/семестр) с индикатором прогресса и очередью задач.

## 3. Способы подачи

Определить единый интерфейс `ReportDeliveryMethod`, реализуемый разными способами доставки одного и того же сгенерированного отчёта.

### 3.1 Экранные формы (on-screen)
- Просмотр отчёта прямо в интерфейсе системы (таблица/дашборд) без обязательного экспорта в файл.
- Поддержка интерактивных фильтров и сортировки поверх уже сгенерированных данных.
- Возможность «превратить» экранную форму в файл одним действием (переход к экспорту без повторного запроса параметров).

### 3.2 Отправка письмом с вложением
- Указание e-mail получателя (в т.ч. не пользователя системы — например, внешний адрес деканата).
- Настраиваемый шаблон письма (тема, текст, подпись отправителя).
- Отчёт прикладывается в выбранном формате (или нескольких форматах одновременно).
- Требуется: очередь отправки, статус доставки (отправлено/ошибка), повторная отправка при сбое, лог отправленных писем (кому, когда, какая форма).

### 3.3 Передача другому пользователю системы (внутренний инструментарий)
- Отчёт направляется конкретному пользователю системы (напр. заведующему кафедрой, декану) как внутреннее уведомление/сообщение с прикреплённым файлом или ссылкой на него.
- Разграничение прав: получатель должен иметь право видеть эти данные (проверка scope — своя ли это группа/кафедра для получателя).
- Уведомление в интерфейсе (badge/inbox) + возможность комментария при передаче («прошу обратить внимание на группу N»).
- Хранение истории переданных отчётов, привязанной к обоим пользователям (отправитель/получатель).

### 3.4 Скачивание
- Прямое скачивание сгенерированного файла из интерфейса.
- Ссылка на скачивание должна быть либо одноразовой/с ограниченным сроком жизни (если отчёт содержит персональные данные), либо защищена правами доступа при повторном обращении.
- История скачиваний пользователя (свои прошлые заказы отчётов, с возможностью повторного скачивания без пересчёта, если данные не изменились).

> Агенту важно спроектировать доставку как **отдельный слой** от генерации: один и тот же `GeneratedReport` (файл + метаданные) может быть одновременно показан на экране, отправлен по почте и передан коллеге — без повторной генерации.

## 4. Меню заказа отчётности

Спроектировать пошаговый UI-флоу («мастер заказа отчёта»), а также механику работы очереди/истории заказов.

### 4.1 Шаги мастера заказа
1. **Выбор формы отчёта** — из перечня раздела 1, сгруппированного по уровню (группа / студент / преподаватель / кафедра-институт / оперативные), с коротким описанием каждой формы.
2. **Выбор области действия** — институт → кафедра → группа/преподаватель/дисциплина (каскадные фильтры, зависящие от прав текущего пользователя: староста видит только свою группу, декан — весь институт).
3. **Выбор периода** — предустановленные пресеты (сегодня/неделя/месяц/семестр) + произвольный диапазон дат.
4. **Дополнительные фильтры формы** — специфичны для типа отчёта (напр. порог % для «хронических прогульщиков», причина отсутствия, тип занятия).
5. **Выбор формата экспорта** — один или несколько из PDF/Excel/Word (чекбоксы).
6. **Выбор способа подачи** — экранный просмотр / email / передача пользователю / скачивание (можно выбрать несколько одновременно, напр. «показать на экране» + «отправить деканату на почту»).
7. **Подтверждение и запуск** — превью параметров заказа, кнопка «Сформировать».

### 4.2 Обработка заказа
- Лёгкие отчёты (одна группа, короткий период) — генерация синхронно, с показом результата сразу.
- Тяжёлые отчёты (институт, семестр, несколько форматов) — постановка в очередь, отчёт о статусе («в очереди» / «формируется» / «готов» / «ошибка»), уведомление по готовности.

### 4.3 Меню «Мои заказы» / история
- Список ранее заказанных отчётов текущего пользователя: дата заказа, тип формы, параметры, статус, доступные действия (повторное скачивание, повторная отправка, повтор заказа с теми же параметрами за новый период).
- Для админов/деканата — расширенный вид: кто и какие отчёты заказывал по их зоне ответственности (аудит).

### 4.4 Шаблоны заказов (опционально, для регулярной отчётности)
- Возможность сохранить комбинацию «форма + фильтры + формат + способ подачи» как именованный шаблон (напр. «Еженедельная сводка деканату») и запускать/планировать по расписанию (cron-подобно), с автоматической отправкой по e-mail без повторного прохождения мастера.
