## 0. Модель ролей — общая картина

Ввести в систему следующие роли (`UserRole`):

| Роль | Как получает | Кто выдаёт |
|---|---|---|
| `guest` / незарегистрированный | — | — |
| `user` (обычный зарегистрированный пользователь) | самостоятельная регистрация | — |
| `teacher_pending` (заявка на статус преподавателя) | пользователь при регистрации указывает "роль: преподаватель" | — |
| `teacher` (подтверждённый преподаватель) | подтверждение заявки | `system_admin` |
| `dean` (декан) | назначение | `system_admin` |
| `system_admin` (системный администратор) | назначение при развёртывании/другим админом | — |

Ключевой принцип: **регистрация ≠ авторизация прав**. Любой человек может зарегистрироваться и указать «я преподаватель», но реальные права преподавателя (доступ к журналам, спискам групп и т.п.) появляются только после ручного подтверждения администратором. До подтверждения пользователь имеет права обычного `user` (минимальные — фактически может пользоваться только тем, что доступно любому зарегистрированному студенту/сотруднику, если такое предусмотрено).

Агенту нужно явно спроектировать эту двухфазность как конечный автомат статуса (`TeacherVerificationStatus`: `not_requested → pending → approved | rejected`), а не как булево поле.

## 1. Регистрация и заявка на статус преподавателя

### 1.1 Форма регистрации
Стандартные поля (ФИО, e-mail, пароль) + блок «Роль в системе»:
- Радио-выбор: «Я студент» / «Я преподаватель».
- При выборе «Я преподаватель» — дополнительные поля для заявки:
  - ФИО (уже есть)
  - Кафедра (выбор из справочника `Department`)
  - Дисциплины, которые ведёт (мультивыбор из справочника `Subject`, опционально — можно уточнить позже)
  - Служебный e-mail университета (если отличается от личного, используемого для входа) — для облегчения верификации
  - Опционально: поле для комментария/подтверждающей информации (напр. номер приказа, ссылка на страницу кафедры)

### 1.2 Что происходит после отправки заявки
- Создаётся `TeacherRequest` со статусом `pending`, привязанный к `user.id`.
- Пользователь получает роль `user` немедленно (может пользоваться системой как обычный аккаунт), но видит в интерфейсе баннер «Заявка на статус преподавателя на рассмотрении».
- `system_admin` получает уведомление о новой заявке (в админ-панели + опционально e-mail).

### 1.3 Рассмотрение заявки администратором
Интерфейс админа должен предоставлять:
- Список заявок с фильтром по статусу (`pending` в первую очередь).
- Карточка заявки: все указанные пользователем данные + дата регистрации + e-mail для связи.
- Действия: **Подтвердить** (→ роль `teacher`, привязка к кафедре/дисциплинам фиксируется как факт) / **Отклонить** (с обязательным указанием причины, которая уходит пользователю) / **Запросить уточнение** (возврат заявки пользователю с комментарием, статус остаётся `pending`, но пользователь видит, что нужно доисправить).
- Лог всех решений (кто, когда, какое решение, комментарий) — обязателен для аудита.

> Агенту зафиксировать: подтверждение выдаёт **привязку к конкретной кафедре/дисциплинам**, а не абстрактную роль «преподаватель вообще» — это определяет, к каким группам/журналам у него будет доступ (см. раздел 2).

## 2. Права доступа роли «преподаватель» (`teacher`)

### 2.1 Просмотр
- Список своих пар (расписание) — только те `Lesson`, где он указан как преподаватель, либо где дисциплина/кафедра совпадает с его привязкой.
- Списки групп, у которых он ведёт занятия (состав студентов, но **не** списки всех студентов института).
- Журнал посещаемости по своим парам — история отметок, кто отмечал (сам/дежурный/автоматически).
- Аналитические формы (из модуля отчётности) — но **со scope, ограниченным его дисциплинами/группами**: он не может заказать сводный отчёт по чужой кафедре.

### 2.2 Управление
- Отметка посещаемости на своей паре (если это не полностью автоматизировано другим модулем — здесь нужно явно уточнить у агента, пересекается ли это с уже существующим механизмом фиксации посещаемости, или преподаватель только просматривает и корректирует).
- Редактирование/оспаривание отметки (напр. изменить «отсутствовал» → «опоздал» с указанием причины) в пределах ограниченного окна времени после пары (антифрод: нельзя менять историю произвольно спустя месяцы без отдельного разрешения).
- Заказ отчётов (мастер заказа из модуля отчётности) в рамках своего scope.
- Передача отчёта другому пользователю системы (напр. заведующему кафедрой) — используя существующий механизм внутренней доставки.

### 2.3 Ограничения (явно прописать как negative-требования)
- Преподаватель **не видит** данные по группам/дисциплинам, к которым не привязан.
- Преподаватель **не может** подтверждать других преподавателей и не видит очередь заявок.
- Преподаватель **не может** выполнять полную выгрузку БД (это прерогатива декана и администратора, см. раздел 3).

## 3. Права декана (`dean`)

### 3.1 Область видимости
- Полный доступ на чтение по своему институту (все кафедры, группы, преподаватели, студенты, журналы посещаемости) — либо по всей организации, если роль вводится в единственном экземпляре (агенту уточнить/предусмотреть оба варианта: `dean` с привязкой к `Institute` и возможность будущего `dean` без привязки — на случай, если институт один).
- Доступ ко всем формам отчётности из модуля отчётности без ограничения scope в пределах своего института.

### 3.2 Выгрузка БД в Excel-книги
Ключевое требование — декан может выполнить **полную выгрузку данных**, а не только заказ готовой аналитической формы:

- **Что выгружается:** агенту предложить состав выгрузки — как минимум сырые таблицы `Lesson`, `AttendanceRecord`, `Student`, `Group`, `Teacher`, `Subject` за выбранный период/институт, без предварительной агрегации (в отличие от аналитических форм из модуля отчётности, которые уже агрегированы).
- **Формат:** одна Excel-книга (`.xlsx`) с несколькими листами — по одному листу на сущность (напр. лист «Занятия», лист «Посещаемость», лист «Студенты» и т.д.), либо декан может выбрать конкретные сущности для выгрузки.
- **Фильтры перед выгрузкой:** период (обязательно, чтобы не тянуть всю историю по умолчанию), кафедра/группа (опционально — по умолчанию весь институт).
- **Производительность:** выгрузка большого объёма данных должна идти через ту же асинхронную очередь, что и тяжёлые отчёты (переиспользовать механизм из модуля отчётности, раздел 4.2 смежного документа), с уведомлением о готовности и скачиванием по ссылке.
- **Аудит:** каждая выгрузка логируется (кто, когда, какой период/scope выгрузил) — это потенциально чувствительные персональные данные (ФИО студентов, посещаемость), поэтому обязательна запись в лог доступа, а по возможности — уведомление системного администратора о факте полной выгрузки.
- **Отличие от «Меню заказа отчётности»:** выгрузка БД — это отдельная, более простая по UI функция («выбрал период → выбрал сущности → скачал сырые данные»), не пошаговый мастер с формами/фильтрами уровня аналитики; агенту не путать её с `ReportType` из модуля отчётности.

### 3.3 Ограничения
- Декан не управляет ролями пользователей (не подтверждает преподавателей) — это остаётся у `system_admin`.
- Декан не может редактировать сырые данные через выгрузку (выгрузка — только на чтение).

## 4. Роль системного администратора (`system_admin`) — в части, касающейся этого документа

- Подтверждение/отклонение заявок на статус преподавателя (раздел 1.3).
- Назначение роли `dean` конкретным пользователям.
- Просмотр аудит-лога: заявки на преподавателя, решения по ним, факты полных выгрузок БД деканом.
- Возможность отозвать роль (`teacher`/`dean`) у пользователя, если она была выдана ошибочно.

## 5. Открытые вопросы для агента (явно зафиксировать в ответе, если решение не очевидно)

1. Может ли один пользователь одновременно иметь роль `teacher` и `dean`? (Вероятно да — декан обычно тоже преподаёт.) Спроектировать роли как **набор** (`roles: UserRole[]`), а не единственное значение, с этим кейсом в уме.
2. Что происходит с уже поданными отчётами/выгрузками, если роль пользователя позже отозвана — сохраняются ли файлы или доступ к ним блокируется?
3. Нужна ли декану возможность выгружать не только свой институт, но и весь вуз (если это предусмотрено оргструктурой) — уточнить, что декан привязан ровно к одному `Institute`, если не сказано иное.
4. Как долго хранится история решений по заявкам преподавателей и логи выгрузок (политика хранения аудита).
